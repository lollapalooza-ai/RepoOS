### **How MLIR is converted into LLVM IR**

In this architecture, "MLIR" refers to the **Custom JSON-based Execution Graph** defined in `component2.py`. The conversion to LLVM IR happens inside **`component4_jit.py`** via the `PolyKernelJIT` class. 

The process follows a two-pass compilation strategy:

#### **Pass 1: Infrastructure & Topology**
*   **Module Setup**: It initializes an `llvmlite.ir.Module` and defines a function signature. It uses a `TYPE_MAP` to convert Python types to LLVM primitives (e.g., Python `float` becomes `ir.DoubleType()`, `str` becomes `ir.PointerType(ir.IntType(8))`).
*   **Basic Block Mapping**: It scans the MLIR for `label` opcodes. For every label found, it appends an `ir.BasicBlock` to the LLVM function. This maps the high-level logic flow to LLVM’s Control Flow Graph (CFG).
*   **Memory Allocation**: It iterates through `memory_allocations` in the JSON and uses `builder.alloca` to reserve stack space for arrays or structs. It also creates stack "slots" for function arguments so they can be mutated.

#### **Pass 2: Instruction Emission**
The compiler iterates through the `operations` list in the MLIR and uses an `ir.IRBuilder` to emit the corresponding LLVM instructions:

*   **Arithmetic**: MLIR `add`, `sub`, `mul`, `div` are mapped to LLVM floating-point instructions (`fadd`, `fsub`, etc.) because the system standardizes on `Double` for math safety.
*   **Memory Access**:

*   **MLIR Solution:** It provides a framework to define "Dialects." Instead of writing a new compiler for every AI chip (TPU, GPU, NPU), you write a dialect that translates the AI graph into a format the chip understands.

### 3. Domain-Specific Languages (DSLs)
If you are building a specialized language—for example, a language for **Image Processing** (like Halide) or **Hardware Description** (like Verilog)—you use MLIR to define your own operations. 
*   You don't have to write your own "optimizer." You just map your language to MLIR, and you instantly get access to years of industry-standard optimization research (like loop unrolling or dead-code elimination).

### 4. Hardware Synthesis (CIRCT)
MLIR is used to design physical computer chips. The **CIRCT** project uses MLIR to represent hardware circuits. It allows designers to optimize a circuit at a high level (logic gates) before "lowering" it to the physical layout (transistors).

### 1. The `MemRef` Dialect (Abstraction)

*   **AoS Layout:** `(i, j) -> (3*i + j)` (Standard interleaved memory)
*   **SoA Layout:** `(i, j) -> (j*N + i)` (Contiguous blocks of Reds, then Greens, then Blues)

To convert AoS to SoA, a developer (or a compiler pass) doesn't rewrite the business logic. They simply apply a **Transformation Pass**. The compiler then mathematically rewrites every index calculation in the entire program to match the new layout.

### 3. The `Transform` Dialect (Deterministic Rewriting)
MLIR has a specific dialect called the **Transform Dialect**. It allows you to write a "recipe" for code optimization. A typical non-AI recipe for AoS to SoA looks like this:
1.  **Identify** all `alloca` operations that create a specific struct.
2.  **Vectorize** the loop processing that struct.
3.  **Decompose** the struct into individual arrays (SoA).
4.  **Rewrite** the `load` and `store` operations to point to the new arrays.

## USER 🧑‍💻

What are the industry standard middle optimizations?

---

## MODEL ✨

"Middle-end" optimizations are the heart of a compiler. They happen after the code has been parsed into an Intermediate Representation (IR) but before it has been turned into machine-specific assembly.

In the industry (LLVM and MLIR), these are generally divided into three tiers:

### 1. Scalar Optimizations (The "Classic" Cleanup)
These are standard in compilers like `gcc`, `clang`, and `rustc`. They treat the code as a stream of simple instructions.

*   **DCE (Dead Code Elimination):** Removing code that runs but whose results are never used. (e.g., calculating a variable that is never read).
*   **Constant Folding & Propagation:** If you write `x = 2 + 2`, the compiler replaces it with `x = 4` at compile time so the CPU never has to do the addition.
*   **GVN (Global Value Numbering):** Detecting when the same value is calculated multiple times and replacing the redundant calculations with a single reference.
*   **SROA (Scalar Replacement of Aggregates):** This is critical for your Poly-Kernel project. It takes a "Struct" (like a Python object) and breaks it into individual variables. This allows the compiler to put those values into **CPU Registers** instead of slow RAM.

### 2. Loop & Affine Optimizations (The "MLIR" Tier)
This is where MLIR is the industry leader. These optimizations understand "Space and Time"—how loops move through memory.

*   **Loop Tiling (Blocking):** Breaking a massive loop into small "tiles" that fit perfectly into the CPU's L1 cache. This prevents "Cache Misses," which are the #1 killer of performance in modern systems.
*   **Loop Unrolling:** Replicating the body of a loop multiple times to reduce the "overhead" of the loop counter (`i++`) and the branch instruction.
*   **Loop Fusion:** If you have two loops that iterate over the same data, the compiler merges them into one. This means the data only has to be loaded from RAM once instead of twice.
*   **Vectorization (SIMD):** Converting a loop that processes one number at a time into a single instruction that processes 4, 8, or 16 numbers simultaneously using special hardware units (like AVX or Neon).

### 3. Memory & Data Flow Optimizations
These focus on how data is laid out and moved.

*   **Inlining:** Taking the code inside a function and "pasting" it directly at the call site. This eliminates the "Function Call Overhead" (pushing/popping from the stack).
*   **LICM (Loop-Invariant Code Motion):** If a calculation inside a loop doesn't change every iteration (e.g., `x = a * b` inside a loop where `a` and `b` are constant), the compiler moves it **outside** the loop so it only runs once.
*   **Escape Analysis:** Determining if a variable "escapes" a function. If it doesn't, the compiler can allocate it on the **Stack** (very fast) instead of the **Heap** (slow).

### How these relate to your "Poly-Kernel" Project

Currently, your project uses a very simple "Middle-End." If you look at `component4_jit.py`, you can see the optimization pass being set up:

## USER 🧑‍💻

How to use custom MLIR dialect?

---

## MODEL ✨

In the formal LLVM ecosystem, using a custom MLIR dialect is a structured process that moves from **Definition** to **Generation** to **Implementation**. 

Unlike the JSON-based "Virtual Dialect" in your Poly-Kernel project, a formal dialect is integrated directly into the C++ compiler infrastructure.

---

### 1. Define the Dialect (TableGen)
Instead of writing C++ classes by hand, you define your dialect in a **TableGen (`.td`)** file. This is a declarative language that describes what your dialect can do.

```tablegen
// MyDialect.td
def My_Dialect : Dialect {
  let name = "poly";
  let cppNamespace = "::mlir::poly";
  let summary = "A dialect for Poly-Kernel acceleration.";
}

// Define a custom Operation
def Poly_AddOp : Poly_Op<"add", [Pure]> {
  let summary = "Addition operation";
  let arguments = (ins F64:$lhs, F64:$rhs);
  let results = (outs F64:$res);
}
```

### 2. Generate C++ Code (`mlir-tblgen`)
You run the MLIR TableGen tool to turn that `.td` file into C++ headers and source files.
*   It creates the `AddOp` class.
*   It creates verification logic (e.g., ensuring `lhs` and `rhs` are actually 64-bit floats).
*   It generates the "Parsing" and "Printing" code so you can read `.mlir` text files.

### 3. Register the Dialect
In your compiler's main entry point, you must tell the **MLIRContext** that your custom dialect exists.

```cpp
#include "MyDialect.h"

int main() {
    mlir::DialectRegistry registry;
    registry.insert<mlir::poly::PolyDialect>(); // Register your dialect
    
    mlir::MLIRContext context(registry);
    context.loadAllAvailableDialects();
    // Now the compiler "understands" the 'poly' prefix
}
```

### 4. Build IR with the Dialect
You use an **`OpBuilder`** to programmatically create code using your dialect. This replaces the part of your code where the AI generates JSON.

```cpp
mlir::OpBuilder builder(&context);
auto lhs = ...; // Get a value
auto rhs = ...; // Get a value

// This creates: %0 = poly.add %arg0, %arg1 : f64
auto addOp = builder.create<mlir::poly::AddOp>(location, lhs, rhs);
```

### 5. Define Lowering (The Conversion)
This is the most important step. You must tell MLIR how to "Lower" your `poly.add` into something else (like the `llvm.add` dialect). You write a **Conversion Pattern**:

```cpp
struct AddLowering : public OpConversionPattern<poly::AddOp> {
  LogicalResult matchAndRewrite(poly::AddOp op, OpAdaptor adaptor,
                                ConversionPatternRewriter &rewriter) const override {
    // Turn 'poly.add' into 'llvm.fadd'
    rewriter.replaceOpWithNewOp<LLVM::FAddOp>(op, adaptor.getLhs(), adaptor.getRhs());
    return success();
  }
};
```

---

### How to apply this to your Poly-Kernel Project?

If you wanted to move from **JSON** to a **Formal Dialect**, your pipeline would change to this:

1.  **AI Generation:** The AI still generates JSON (because it's easy for LLMs).
2.  **The "Lifting" Script:** You write a Python script that reads the JSON and uses the `mlir` Python bindings to create a formal `poly.add` operation.
3.  **The Optimization Pipeline:** You pass that formal IR through the standard MLIR `PassManager`. You can now run `mlir-opt --affine-loop-fusion --cse --symbol-dce`.
4.  **Final Lowering:** You use the built-in `mlir-translate` to turn your optimized `poly` IR into standard LLVM IR for the final JIT.

### Summary
*   **TableGen**: Defines the rules.
*   **MLIRContext**: The "brain" that stores the registered dialects.
*   **OpBuilder**: The "hand" that writes the code.
*   **PassManager**: The "editor" that runs industry-standard middle optimizations.
